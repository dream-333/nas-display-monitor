# 铁牛 NAS Docker 部署

目标系统为铁牛 NAS（Debian 底层，不支持安装 DEB/FPK），硬件按已确认的 Centerm Zero1 pro、x86_64、IT8613 配置。通过 Docker 独立部署应用，部署需要 Docker，以及可导入本镜像并支持 Compose 配置的管理界面；具体界面能力待核对。镜像内包含 NAS Display 1.5.2 网页、采集器、风扇控制服务、smartctl，以及适配 `6.1.0-39-amd64` 的 IT8613 驱动和依赖模块，无需在容器内安装 Python 或执行交互式初始化。

## 推荐入口：飞牛式 Compose 项目包

无终端部署请使用 `NAS-Display-Compose-1.5.2-amd64.zip`，按[图形界面安装说明](DOCKER-GUI.zh-CN.md)操作：上传整个目录 → Docker / Compose 创建项目 → 选择目录并粘贴 docker-compose.yml → 设置初始密码 → 构建、启动。

这个包携带已编译运行环境，在 NAS 上仅离线组装镜像；不需要镜像导入按钮、镜像仓库、终端或编译器。具体铁牛界面仍需支持 Compose 的本地 build 与编排中的权限配置。下文保留另一种 `NAS-Display-Docker-...zip` 镜像导入包的说明，两个包不要混用。

## 图形界面部署（不需要终端）

铁牛目标系统没有终端，安装、设置初始密码、启动和查看状态均应通过网页完成。

目前已从[铁牛官方产品页](https://www.tieniu-ai.com/zero1-pro.html)确认其提供 Docker；公开的[官方帮助文档](https://www.tieniu-ai.com/doc/升腾Zero1中文帮助文档.pdf)未找到 Docker 创建容器的说明。因此，尚未确认当前铁牛版本是否支持离线镜像导入、Compose 编排及所需权限字段。以下是本应用的部署要求和条件步骤，不代表已在铁牛实测的菜单名称。飞牛的界面不能直接当作铁牛的界面使用。

### 1. 先确认 Docker 界面提供哪些功能

打开铁牛桌面的 Docker 应用，查看镜像管理和创建应用页面：

| 界面能力 | 使用方式 |
|---|---|
| 支持导入镜像文件，并支持 Compose / 编排 | 可以使用现有离线交付包，按下方步骤部署 |
| 只支持从镜像仓库下载，并支持 Compose / 编排 | 需要先将本镜像发布到可访问的仓库；目前尚未发布，不能直接搜索下载 nas-display:1.5.2 |
| 只有单容器创建表单 | 需要核对网络、挂载、启动入口、环境变量与权限选项；当前方案包含四个服务，不能只创建网页容器就视为完整部署 |

如果界面没有对应入口，提供 Docker 首页及创建页面截图即可继续适配，不需要执行命令，也不要开启 SSH。

### 2. 导入离线镜像（仅在界面支持时）

在电脑上解压 `NAS-Display-Docker-1.5.2-amd64.zip`。在 Docker 的镜像导入入口选择其中的 `NAS-Display-Docker-1.5.2-amd64.tar.gz`；如果界面只接受 `.tar`，可在电脑上用解压软件将 `.gz` 解开一层，保留里面的 `.tar` 文件，不要继续展开镜像内部文件。

ZIP 是交付包，不能当作镜像直接导入。也不要使用“导入容器文件系统”的功能代替加载镜像，它会丢失镜像启动配置。导入完成后应能看到 `nas-display:1.5.2` 镜像。

### 3. 创建编排并设置登录密码（仅在界面支持时）

将交付目录上传到 NAS 的持久存储目录。在 Compose / 编排创建入口选择交付包中的 `compose.yaml`，或把文件全文粘贴到 YAML 编辑框。项目名可用 `nas-display`，之后更新保持项目名和存储位置不变。

**首次启动前**，在 `nas-display` 服务现有的 `environment` 内添加下面一项，并把值改成自己设置的密码。这是 YAML 配置，不是终端命令；与 `NAS_DISPLAY_PORT` 保持相同缩进，不要新建第二个 environment 区块：

```yaml
      NAS_DISPLAY_ADMIN_PASSWORD: '在这里填写自己设置的初始密码'
```

为了避免 YAML 和 Compose 转义问题，初始密码可用至少 12 位随机英文字母和数字；这里的中文占位内容必须替换，不是默认密码。若创建表单提供环境变量输入框，变量名填写 `NAS_DISPLAY_ADMIN_PASSWORD`，变量值填写自己的密码即可。

此密码仅首次初始化生效。容器配置和编排文件中会保留该值；首次登录后可在应用“账户设置”修改密码，再从编排移除这一项并通过界面重新创建容器，保留数据卷。不要为了改密码删除数据卷。

交付包内四个服务使用同一个已导入镜像，无需构建。保持其挂载、启动入口和权限配置，然后点击创建/启动。若界面要求强制拉取镜像，应先关闭该选项；本地镜像尚未发布到远程仓库。

### 4. 打开应用与查看状态

在浏览器访问 `http://NAS的IP:8787`，使用上一步设置的密码登录，无需用户名。首次启动自动创建配置并采集；不连接屏幕也可使用。进入“屏幕与采集”填写屏幕 IP、端口 44445，保存并启用发送。屏幕须已升级免配对固件。

在网页“硬件准备”和风扇页面查看驱动结果；需要排查时，在 Docker 界面打开 driver、fans、smart、nas-display 对应容器的日志。无需进入容器终端。

如果 8787 被占用，在编排中将 `NAS_DISPLAY_PORT` 的值改为 `8788`，通过界面应用配置后访问新端口。host 网络无需端口映射。

## 配置保留与更新

Compose 自动建立网页配置、风扇曲线/恢复快照、风扇 socket、SMART 缓存、驱动检测状态五个数据卷。更新时在 Docker 界面导入新镜像、更新原有编排并重新创建容器，保留项目名与数据卷。不要勾选“删除数据卷/清除数据”。重启不会重置密码、屏幕配置和已启用曲线。

正常停止风扇容器会恢复接管前的模式；启动会恢复已启用曲线。强制杀死容器或断电时无法执行停止恢复。

如有此前导出的 config.json，可在网页导入。旧 token 会被忽略，导入后默认暂停发送，确认设置后保存启用。管理员密码采用容器自己的持久配置。

如果此前已启动容器且未指定初始密码，随机密码保存在该容器数据卷的 initial-password.txt。新增环境变量不会覆盖已有密码；若 Docker 界面支持浏览数据卷，可从界面读取该文件，否则需按实际界面另行处理，不应要求用户运行终端命令。

## 本机硬件

容器通过宿主机的 proc/sys 和设备接口采集与控制硬件。driver 容器启动时检查运行中的内核、主板、现有模块和权限：

1. 已有 IT8613 接口时沿用，不重复加载。
2. 只有 `6.1.0-39-amd64` / x86_64、DMI 为 Centerm / Zero1 pro、没有已加载的冲突 it87 模块时，才尝试加载镜像中的专用模块及 hwmon-vid 依赖。
3. 加载前核对模块 SHA256；不使用 force_id、强制版本参数、关闭签名检查或卸载原驱动。
4. 签名限制、权限不足、内核不匹配或资源冲突会显示在网页“硬件准备”区域，其他监控继续运行。

用户无需安装 DEB/FPK、内核头文件或编译器；模块在镜像构建阶段编译。这里加载的是宿主机内核模块，必须由铁牛 Docker 允许 driver 容器使用 SYS_MODULE 权限。当前模块未签名；Secure Boot/Lockdown 或强制模块签名环境可能拒绝加载。内核升级后必须重新适配，不能通过修改版本字符串复用旧模块。

driver 容器保持运行，宿主机重启后由 Docker 自动重新执行检查和加载。停止容器不卸载内核模块；fans 容器正常停止时仍负责恢复风扇原有模式。在编排中将 driver 的 `NAS_DISPLAY_DRIVER_POLICY` 值改为 `existing-only` 可禁止主动加载，然后通过界面重新创建容器。查看结果可使用应用网页或 Docker 界面的 driver 容器日志。

| 功能 | 容器配置 |
|---|---|
| CPU、内存、网卡、CPU/SYS 温度、转速、NVMe 原生温度 | 默认开启；从只读宿主机 proc/sys 采集 |
| UDP 屏幕 | 默认可用；主机网络，填写屏幕的 IPv4 地址 |
| IT8613 调速与曲线 | fans 容器，持久化恢复快照/曲线；在驱动检查完成后启动 |
| SATA/USB 等硬盘温度 | smart 容器定时采集并写缓存；沿用不主动唤醒休眠盘的策略 |
| Intel 核显 | 自动读取已暴露的原生接口；i915 引擎占用率需要 perf 权限，默认未额外开放，受限时显示 -- |
| USB 屏幕 | 使用下方 USB 配置 |

driver 为独立 root 进程，仅授予 SYS_MODULE 并关闭其 AppArmor 限制，用于加载内置固定模块；不挂载宿主机模块目录写入安装文件。fans 为独立 root 进程，具有 sysfs 写权限并关闭该容器的 AppArmor 限制；smart 为独立 root 进程，只运行固定 SMART 查询并有块设备访问和 SYS_RAWIO 权限。网页仍以普通用户运行，不挂载 Docker socket，不使用 privileged。铁牛的实际驱动、设备权限和调速响应需要在这台 NAS 验证。

USB 连接需要额外设备权限和正确的设备所属组。交付包包含 `compose.usb.yaml`，但铁牛界面能否添加覆盖配置、展示 USB 设备权限尚未确认。无终端部署先使用 Wi-Fi UDP；需要 USB 时，应依据铁牛的设备管理/容器创建界面核对后补全，不能将默认组号 20 当作这台机器的实测结果。

## 开发者构建和检查（不属于铁牛安装步骤）

镜像构建使用 Debian 2025-09-08 的签名软件源快照、`6.1.148-1` 内核头文件与 GCC 12。驱动沿用项目固定源码，仅增加 Linux 6.1 的 class_create 参数兼容，传感器和调速逻辑不变。镜像的 `/opt/it8613/MODULES.json` 记录内核、模块摘要、编译器和来源；同目录携带修改后的驱动源码、对应内核源码压缩包及内核配置。

在工程根目录：

```bash
docker build -t nas-display:1.5.2 .
docker compose up -d
```

工程中的 USB 配置路径为 `src/host/docker/compose.usb.yaml`。安装目录不依赖工程的 Python 环境或构建缓存；交付镜像可以通过 docker load 离线导入。

```bash
.venv/bin/python tools/verify_docker.py --engine docker --image nas-display:1.5.2
```

检查使用临时容器和数据卷，验证初次登录、真实采样/UDP、重启、配置保留和健康检查，以及模拟硬件目录下的风扇 socket、SMART 缓存通信和驱动拒绝加载报告。开发机可用 `--engine podman` 验证同一镜像。Docker 引擎和铁牛硬件实机验收需另行记录，不能用 Podman 结果代替。

导出离线安装 ZIP：

```bash
.venv/bin/python tools/package_docker.py --image nas-display:1.5.2
```

输出在 `.build/docker/`，包含 docker load 镜像、Compose、USB 配置和摘要。本次开发机以 Podman 构建并验证：176 项 Python 回归和四容器通信通过；尚未在目标铁牛 Docker 引擎中部署，也未实测目标内核的模块加载、物理风扇写入、USB 热插拔和硬盘 SMART 读取。

构建配置依据 [Docker Compose 服务说明](https://docs.docker.com/reference/compose-file/services/)。本交付针对上述铁牛 x86_64 主机，不提供 Windows/macOS Docker Desktop 或 ARM 适配。
